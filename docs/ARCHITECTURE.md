# Архитектура и подготовка к защите

## Файлы исходного кода

| Файл | Ответственность |

## Что происходит при внесении денег

Для счёта с $100.00 пользователь выбирает Deposit и вводит $12.34.

1. `parse_money` получает целое `1234`, без двоичной дроби `double`.
2. Приложение берёт межпроцессную блокировку каталога. Ожидание ограничено
   примерно пятью секундами, поэтому заблокированная сессия не висит бесконечно.
3. Проверяется версия текстового снимка. При необходимости он восстанавливается.
4. Начинается `BEGIN IMMEDIATE`; счёт заново читается из базы по **номеру и ID
   текущего владельца**. Проверяется тип, сумма и предел нового баланса.
5. В одной SQL-транзакции баланс становится `11234`, а в журнал добавляется
   `deposit 1234` с текущей локальной датой. При сбое на этом этапе откатятся оба изменения.
6. По ещё не зафиксированному состоянию этой же SQL-сессии создаются три текстовых
   файла и файл версии в новом каталоге. Проверяются `fprintf`, `fflush`, `fsync`
   и `fclose`; ошибка останавливает фиксацию.
7. Выполняется COMMIT. Затем `.current` атомарно переключается на готовый каталог.
8. Блокировка снимается. Дальнейшие экраны заново читают SQLite, анализатор —
   актуальный `transactions.txt`. Старой копии баланса в сессии нет.

При добавлении транзакции новый текст журнала содержит прежние строки и новую
строку в конце. Физически публикуется полный снимок: открытие общего файла в `a`
не смогло бы само обеспечить согласованность с изменением баланса и бонусной БД.
Требование сохранять операции выполнено; порядок строк определяется ID операции.

SQLite предоставляет атомарность своей транзакции. Подробности поведения при
сбоях описаны в [документации SQLite](https://www.sqlite.org/atomiccommit.html).
Наш код отдельно решает задачу текстовых представлений и восстановления между
COMMIT базы и публикацией снимка. Эти два шага не объявляются одной атомарной записью.

## Структура базы

- `users`: уникальные имена и хеши, без открытых паролей.
- `accounts`: номер, владелец, дата, страна, телефон, тип, текущий и начальный
  баланс, признак активности. Номер уникален и после архивирования.
- `transactions`: неизменяемые строки депозитов и снятий, связанные с номером счёта.
- `notifications`: получатель, номер переданного счёта, имя отправителя и время.
- `metadata`: версия данных для восстановления текстового представления.

Включены внешние ключи, ограничения на диапазоны баланса и типы операций,
индексы для истории и уведомлений. SQLite работает в WAL-режиме с
`synchronous=FULL`. SQL-параметры передаются через bind-функции, пользовательский
текст не вставляется в SQL-код. Файловая блокировка объединяет доступ к SQLite
и публикацию представлений между процессами нашего приложения.

При запуске выполняются `quick_check`, `foreign_key_check`, проверка равенства
`текущий баланс = начальный баланс + депозиты − снятия` и проверка промежуточных
балансов по порядку журнала. История fixed-счёта с движением средств отклоняется.
При некорректном импорте SQL-транзакция откатывается, оригинальные текстовые
файлы не подменяются частично импортированными данными.

## Владение, удаление, уведомления

Каждая изменяющая операция повторно проверяет владельца внутри транзакции.
Одной проверки при показе меню недостаточно: другая сессия могла передать счёт.
Регистрация и номер счёта защищены также UNIQUE-ограничениями базы, поэтому
параллельные процессы не обходят проверку дубликатов.

Удаление делает счёт неактивным. Пользователь больше не видит его в списке;
текстовые представления содержат активные счета и их историю. Архивные данные
сохраняются в SQLite. Повторное использование номера запрещено, чтобы новый
счёт не получил старую историю по совпавшему идентификатору.

Передача изменяет `owner` и добавляет уведомление в той же SQL-транзакции.
Если COMMIT не состоялся, уведомление не появится. Получатель, ожидающий ввод,
опрашивает свой индекс уведомлений через `select` с периодом 200 мс. На каждое
полученное событие выводится сообщение; курсор ID предотвращает повтор в этом
сеансе. При недоступном получателе запись остаётся в базе для просмотра после входа.

## Анализатор на небольшом примере

Из строк всех счетов `spending_read` выбирает только запрошенный номер.
Допустим, для него записаны депозиты $5.96 и снятия $4.04.
Суммы в копейках — 596 и 404; знаменатель — 1000.

```text
(596 × 100 + 1000 / 2) / 1000 = 60  (целочисленное деление)
```

Значит категория `saver`. Если депозит — $5.94, снятие — $4.06,
получится 59 и категория `moderate`. Округление после классификации дало бы
неверный ответ на границе, поэтому порядок важен.

Лимит суммы журнала обеспечивает отсутствие переполнения при умножении на 100.
Пустой журнал обрабатывается до деления; ошибки чтения и неверные строки
не превращаются в категорию `spender` или в сообщение об отсутствии истории.

Начальный остаток отделён от отслеживаемых операций. Например, из остатка $100
можно за рассматриваемый период внести $3 и снять $7: 30% и `spender`, хотя
баланс остаётся положительным. Классификация описывает поток операций периода,
а не абсолютный размер накоплений и не решение о выдаче кредита.

## Память и ошибки

Строки терминала имеют фиксированные ограниченные буферы, ввод длиннее лимита
полностью отбрасывается до следующей строки. Телефон хранится строкой, чтобы
не потерять `+` и ведущие нули. `getline` в анализаторе освобождается через `free`
на всех выходах; входной файл предварительно ограничен размером. SQLite statement
всегда завершается через `sqlite3_finalize`, сообщения SQLite — через `sqlite3_free`.
Файлы, соединение и дескриптор блокировки имеют явные места закрытия.

Открытые пароли не записываются в файлы. Временные буферы пароля и производного
ключа очищаются через `OPENSSL_cleanse`. Терминальное эхо выключается только
для интерактивного ввода пароля и восстанавливается при EOF, Ctrl+C и SIGTERM.
Необрабатываемый SIGKILL восстановить настройки терминала не позволяет; это
ограничение остановки процесса ОС, а не успешный программный выход.

## Вопросы перед защитой

1. Найдите в `account_transact` место, где обновляется баланс и добавляется строка
   истории. Объясните, что случится при ошибке между ними.
2. Объясните различие между номером счёта, ID пользователя и ID строки записи.
   Почему нельзя повторно выдавать номер архивного счёта?
3. До запуска предскажите категории для 596/404, 594/406 и 395/605 копеек.
4. Объясните, почему одних текстовых `fprintf` в два файла недостаточно для
   восстановления после аварии и какую роль играет версия снимка.
5. Откройте два терминала и объясните, почему старая сессия владельца не может
   снять деньги со счёта после передачи другому пользователю.
6. Покажите, где освобождаются динамические буферы и SQLite statements.

Материал помогает подготовиться. Устное объяснение и предсказание нового примера
на месте остаются отдельной частью аудита, которую автоматические тесты не подтверждают.
