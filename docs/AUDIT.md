# Карта требований и проверок

Основание — предоставленное `teller-system__ts.md`, включая AUDIT и все бонусы.
Проверка запускается командой `make check`; дополнительные проверки —
`make analyze`, `make stress`, на Linux также `make fuzz`.

| Пункт аудита | Реализация / проверка |
| --- | --- |
| Требуемые файлы и структура | Все `data/*.txt`, Makefile, `src/{main,auth,system,header,analyzer}` присутствуют; дополнительные файлы разделяют ответственность |
| Сборка Makefile | C11, строгие предупреждения `-Wall -Wextra -Wpedantic -Werror`, GCC и Clang в CI |

## Все бонусы

| Бонус | Что сделано |
| --- | --- |
| Подробная статистика | Число депозитов и снятий, суммы обоих видов, округлённый процент рядом с категорией |
| Мгновенное уведомление получателя | Проверяется настоящий второй процесс, ожидающий ввода; Enter не требуется |
| Улучшенный терминальный интерфейс | Таблица счетов, компактное циклическое меню, скрытый пароль, понятные ошибки, сигналы и EOF |
| Хеш вместо открытого пароля | OpenSSL PBKDF2-HMAC-SHA256, 600 000 итераций, индивидуальная случайная соль |
| Реляционная база | SQLite, внешние ключи, ограничения, индексы, атомарные бизнес-операции |
| Собственный Makefile | Обычная сборка, unit, audit, sanitize, stress, fuzz, analyze и clean |
| Дополнительные возможности | Автовосстановление текстовых снимков, архив истории, проверка целостности, параллельные сессии, строгие денежные и календарные ограничения |
| Переработка starter | Безопасная авторизация, нормализованный импорт, отсутствие dangling pointer, итеративное меню, отсутствие небезопасного scanf-ввода |

## Проверки сверх основного аудита

- 100 000 денежных значений проверяются через форматирование и обратный разбор.
- Миллион мутаций денежных, календарных и строковых полей исполняются под санитайзерами.
- 120 операций сравниваются с независимой моделью баланса на Python, включая
  заведомо недопустимые снятия.
- 16 конкурирующих запросов на снятие $10 из $100 дают ровно 10 записей и баланс 0.
- Шесть одновременных регистраций одного имени дают ровно одного пользователя.
- Четыре аварийных остановки: после изменения баланса, до COMMIT, после COMMIT,
  после публикации. Проверяется, что нет осиротевших или пропавших операций.
- 12 повреждённых вариантов импорта отклоняются с сохранением исходных файлов.
- Неправильные пользователи, дубликаты номеров, неверные даты, бинарные строки,
  невозможная история, повреждённая база, FIFO и заблокированный каталог.
- Повреждённые текстовые представления восстанавливаются из корректной базы.
- Ввод длиной 10 000 символов, EOF посреди действия, скрытие пароля и восстановление
  эха после SIGTERM проверяются через настоящий псевдотерминал.

## Уточнения для аудитора

SQLite является основным хранилищем, как допускает примечание аудита о выборе
метода хранения. Текстовые файлы дополнительно сохраняются в требуемом формате.
После инициализации это символьные ссылки на опубликованный снимок; обычное
чтение файлов остаётся прежним. Новые операции добавляются в конец логической
истории; безопасная публикация переписывает её полный снимок.

Пароль Marcus проверяется через хеш, а не сравнением с открытой строкой в файле:
это необходимо для обязательного бонуса хеширования. Учебные исходные пароли
Alice и Michel публичны; пользовательские пароли в репозиторий не входят.

Проценты — простой расчёт из ТЗ. Начальный остаток отделён от последующих
депозитов и снятий. Удаление архивирует данные в БД и убирает их из активного
текстового представления. Номер счёта глобально уникален, поскольку формат
истории не содержит ID владельца и не позволяет различить два одинаковых номера.

Устные пункты аудита требуют личного объяснения. Для подготовки есть
ARCHITECTURE.md; автоматическое прохождение этих пунктов не заявляется.
